---
title: PositionComposer
description: Keeps a target at a chosen screen position with a dead zone, hard limit, and damping.
nav: 13
---

Two-stage positioning: first dollies along the camera's own forward axis until `target` sits at `cameraDistance` (or the `depthDeadZone` edge), then shifts sideways until it lands at `screenPosition` (or the `deadZone`/`hardLimit` edge) - the lateral stage uses the same framing model as [`RotationComposer`](/aim/rotation-composer). `damping` eases both stages.

It's the natural fit for a camera whose **rotation stays fixed** - a top-down or 2.5D side-scroller, following the player positionally without ever re-aiming. A `<VirtualCamera>` doesn't require an Aim at all; with none mounted, rotation just stays wherever it started (the real camera's own pristine config, or `initialState`):

```tsx
<VirtualCamera name="platformer-cam" priority={10}>
  <Body.PositionComposer target={playerRef} cameraDistance={12} deadZone={[0.15, 0.1]} damping={0.3} />
</VirtualCamera>
```

See [Ordering with Aim](#ordering-with-aim) below for why pairing this with an Aim that re-centers every frame (`HardLookAt`) undoes exactly the framing behavior that makes it useful in the first place.

## Props

| Prop           | Type                 | Default   | |
| -------------- | -------------------- | --------- | - |
| `target`       | `Target`             | -         | Tracking Target - the camera composes its shot around this position/object's world position. |
| `cameraDistance` | `number`           | `10`      | Desired distance from the camera to the target, along the camera's own forward axis. |
| `depthDeadZone` | `number`            | `0`       | How far the target's depth can drift from `cameraDistance` with no dolly reaction at all - world units along the camera's forward axis. `0` = none, always reacts. |
| `screenPosition` | `[number, number]` | `[0, 0]`  | Where the target should land on screen. `0` = center, `±1` = edge. |
| `deadZone`     | `[number, number]`   | `[0, 0]`  | How far the target can drift from `screenPosition` with no lateral reaction at all - same unit as `screenPosition` itself (`1` reaches the frame edge). `[0, 0]` = none, always reacts. |
| `damping`      | `DampingConstant`    | `0`       | Seconds to catch up to the desired depth and the dead zone's edge once the target steps outside either - the dolly stage reacts to `depthDeadZone`, the lateral stage to `deadZone`. `0` = hard, instant snap to both. |
| `hardLimit`    | `[number, number]`   | `[0, 0]`  | A second, normally larger reach the target may never visually drift past - enforced instantly, bypassing `damping`, after the damped dead-zone pass. `[0, 0]` = no enforcement. |
| `radius`       | `number`             | -         | Target's own bounding-sphere radius - `deadZone`/`hardLimit` react to its nearest edge, not its center. Ignored if `size` is given. |
| `size`         | `Vector3`            | -         | Target's full box dimensions - takes priority over `radius`. Auto-detected from a `Mesh`/`Line`/`Points` target's own geometry when neither is given. |
| `debug`        | `boolean`            | `false`   | Draws `deadZone`/`hardLimit` as bordered, dimmed boxes over the canvas - see [Debug Zones](/debugging/debug-zones). |

`depthDeadZone` and `deadZone` react to different quantities - world-space distance versus screen-space position - so they don't share a threshold, and a target can sit well inside one while triggering the other. At a camera angle far from 0° (straight ahead) or 90° (straight down), the same world-space movement can register very differently on each axis, so keep both at a comparable scale rather than leaving one at `0` and the other generous - otherwise one axis reacts to everything while the other stays quiet, which reads as the camera switching behavior depending on where the target is on screen. `depthDeadZone` has no visual representation in `debug` - it isn't a screen-space rectangle like `deadZone`/`hardLimit`.

## Ordering with Aim

Body always runs before Aim, so the dolly/screen-position math reads whatever `out.quaternion`/`out.fov` Aim wrote on the *previous* frame, not this one - a one-frame lag that's structural, not a bug: Body has to run first so Aim can react to the position it just chose, which means Body itself can only ever see last frame's rotation.

`HardLookAt` rotates to put the target dead-center *every single frame*, regardless of where Body just put the camera - so even with the default `screenPosition: [0, 0]`, it quietly defeats the whole point of a `deadZone`: the target visually never appears to drift at all, since rotation re-centers it before you'd ever see the slack `deadZone` was supposed to allow. Nothing breaks, but the framing behavior you added `deadZone`/`hardLimit` for becomes invisible.

A genuine **non-zero** `screenPosition` paired with `HardLookAt` is worse - a real feedback loop: Body pushes the target off-center based on last frame's rotation, `HardLookAt` immediately re-centers it with a new rotation, and the next frame Body tries again. The shot settles into a stable orbit instead of the position you asked for.

Either way, an Aim that reacts to the target's position at all fights `PositionComposer`. Use no Aim (a fixed rotation, see above), `RotateWithFollowTarget` (which never looks at position, only the target's own rotation), or [`RotationComposer`](/aim/rotation-composer) with the **same** `screenPosition` and a non-zero `deadZone` on both sides - see its own page for why the dead zone specifically is required on both, not just one.

## Target extent (`radius`/`size`)

Without `radius`/`size`, `deadZone`/`hardLimit` react to the target's exact center point, so a target with real, on-screen size can visually leave the zone well before its center does. `radius`/`size` react to its true edge instead. Auto-detection recomputes the bounds only once by default; call `recalculateSize()` (via `ref`) after a target deforms (a `SkinnedMesh` bone animation, a mutated `BufferGeometry`) to force a fresh measurement on the next frame.

## `ref`

```tsx
const bodyRef = useRef<PositionComposerBody>(null);
```

Gives you the underlying `PositionComposerBody` - read or write any prop's field directly, and call `recalculateSize()`.
